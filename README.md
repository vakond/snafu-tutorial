### TL;DR (СД;НЧ) Правила SNAFU

1. [Контекст превыше всего. Не отбрасывайте контекст без
нужды](https://github.com/vakond/snafu-tutorial/blob/main/README.md/#rule1)

2. [Описывайте ошибки на уровне модуля, а не крейта. Каждый нетривиальный модуль
будет иметь свой набор ошибок. Иерархия ошибок будет воспроизводить иерархию
модулей](https://github.com/vakond/snafu-tutorial/blob/main/README.md/#rule2)

3. [Добавляйте в ошибку поле source (см. ниже) для сохранения связи
с "родительской" ошибкой](https://github.com/vakond/snafu-tutorial/blob/main/README.md/#rule3)

4. [При обработке ошибки используйте селекторы контекста (см. ниже), а не сами типы
ошибок](https://github.com/vakond/snafu-tutorial/blob/main/README.md/#rule4)

5. [Не переиспользуйте типы: в разных контекстах должны появляться разные
ошибки](https://github.com/vakond/snafu-tutorial/blob/main/README.md/#rule5)

6. [Предоставьте выбор формата и объёма сообщения об ошибке самому верхнему
уровню](https://github.com/vakond/snafu-tutorial/blob/main/README.md/#rule6)

7. [Проектируйте сверху вниз: сначала ошибки модуля, потом ошибки зависимых
модулей](https://github.com/vakond/snafu-tutorial/blob/main/README.md/#rule7)

8. [Субъективная "перегрузка" модуля ошибками является сигналом о желательности рефакторинга
для разбиения модуля на подмодули](https://github.com/vakond/snafu-tutorial/blob/main/README.md/#rule8)

### Преамбула

Обработка ошибок – часто болезненная тема программирования. Это необходимая,
но, скажем прямо, обычно скучноватая часть работы, отвлекающая от создания и
реализации увлекательных алгоритмов. Как бы она ни реализовывалась – через
числовые коды возврата, исключения или монады, – обработка ошибок порождает
избыточные программные строки (бойлерплейт), что увеличивает когнитивную
нагрузку на разработчика.

Проектировщики языка Rust сделали попытку выбрать лучшие идеи по обработке
ошибок для реализации в этом популярном языке программирования. Rust не
отказывается от исключений (`panic`), но в качестве основной технологии предлагает
монаду `Result` (тип, инкапсулирующий значение, которое может быть
ошибочным). `Result` применяется для обработки "обычных" ошибок, `panic` для ошибок,
"которые не должны возникать". Эта заметка посвящена философии и практике крейта
[**SNAFU**](https://docs.rs/snafu/latest/snafu), предназначенного для удобного генерирования `Result` с контекстом.

По ходу обсуждения будем иллюстрировать идеи на примере реализации разных
вариантов бесполезной утилиты командной строки под названием **SCREP** – Simple
Config Reader & Expression Parser. Она предназначена для поиска по содержанию
файлов в текстовом формате Unix Conf, содержащем параметры и их значения через
пробел и позволяющем вставлять комментарии. Типичный файл в таком формате –
известный каждому пользователю Linux файл resolv.conf, содержание которого может
выглядеть так:

```
# Generated by resolvconf
search lan
nameserver 192.168.1.1 # мой роутер
nameserver fd84:561e:cc37::1
```

Для краткости весь программный код, хотя и разбитый на модули (что важно для
иллюстрации обработки ошибок), будем размещать в единственном файле `main.rs`,
который можно просто скопировать в дефолтный проект, созданный командой `cargo new`.

### Белая магия знака вопроса

Rust предоставляет краткий "магический" способ записи обработки
ошибок. Например, в функции построчного чтения и вывода файла `reader::read()` мы
можем обработать (в данном случае пробросить "наверх" в вызывающую функцию)
ошибки ввода-вывода таким образом:

<summary markdown="span">Программа screp 0.1.0: читать строки из stdin и выводить их в stdout</summary>

```Rust
//! main.rs

fn main() {
    if let Err(err) = rep::process() {
        eprintln!("{err}");
        std::process::exit(1)
    }
}

mod rep {
    use std::io;

    pub fn process() -> io::Result<()> {
        reader::read(io::stdin().lock())
    }

    mod reader {
        use std::io;
         
        pub fn read<R: io::BufRead>(reader: R) -> io::Result<()> {
            for line in reader.lines() {
                println!("{}", line?);
            }
            Ok(())
        }
    }
}
```
</details>

----

Программный код выглядит "чистым" благодаря тому, что знак вопроса в контексте
`Result` (знак вопроса допускается также в контексте `Option`) раскрывается
компилятором в оператор match:

```Rust
line?
```
=>
```Rust
match line {
    Ok(line) => line,
    Err(err) => return Err(err)
}
```

Таким образом, как будто удалось взять лучшее из двух миров – возможность
писать код, почти свободный от громоздкой явной обработки ошибок (преимущество
при использовании исключений), при этом сохраняющий обязательность обработки,
простоту и локальность технологии возврата ошибки.

### Чёрная магия `Box<dyn Error>`

Нет, не всё так просто.

Могут возникнуть несовместимости типов, связанные с устройством генерика
`Result<T, E>`, потому что функция возвращает только один конкретный `Result` для
конкретной ошибки `E`. Например, при наивной попытке совместить обработку ошибок
ввода-вывода и парсинга получаем некомпилируемую программу:

```Rust
pub fn read<R: io::BufRead>(reader: R) -> io::Result<()> {
    for line in reader.lines() {
        let (param, value) = parser::parse(line?)?;
        println!("{param} = {value}");
    }
    Ok(())
}
```
```
error[E0277]: `?` couldn't convert the error to `std::io::Error`
pub fn read<R: io::BufRead>(reader: R) -> io::Result<()> {
					  -------------- expected `std::io::Error`
```

Одно из решений этой проблемы – реализованное в стандартной библиотеке
соглашение, что все типы ошибок неявно конвертируются в тип
`Box<dyn std::error::Error + Send + Sync + 'static>`, который и должны возвращать
функции. Громоздкость конструкций преодолевается применением крейтов вроде
[**anyhow**](https://docs.rs/anyhow/latest/anyhow). Но такое решение во многих случаях неудовлетворительно, так как
"стирает" информацию о типах, обедняя тем самым контекст ошибки.

<details>
<summary markdown="span">Программа screp 0.2.0: читать строки из файла, токенизировать их и выводить токены</summary>

```Rust
//! main.rs

pub type GenericError = Box<dyn std::error::Error + Send + Sync + 'static>;
pub type GenericResult<T> = Result<T, GenericError>;

fn main() {
    let mut args = std::env::args();
    let _ = args.next().expect("Отсутствует имя файла программы");
    let file = args.next().expect("Не задано имя входного файла");
    if let Err(err) = rep::process(file) {
        eprintln!("{err}");
        std::process::exit(1)
    }
}

mod rep {
    use std::{fs, io};

    pub fn process(file: String) -> crate::GenericResult<()> {
        let file = fs::File::open(file)?;
        reader::read(io::BufReader::new(file))
    }

    mod reader {
	use std::io;

	pub fn read<R: io::BufRead>(reader: R) -> crate::GenericResult<()> {
	    for line in reader.lines() {
                let (param, value) = parser::parse(line?)?;
                println!("{param} = {value}");
	    }
	    Ok(())
	}

	mod parser {
	    #[derive(Debug)]
	    struct Error {}
	    impl std::fmt::Display for Error {
                fn fmt(&self, f: &mut std::fmt::Formatter) -> std::fmt::Result {
                    write!(f, "Parser Error")
                }
	    }
	    impl std::error::Error for Error {}

	    pub fn parse(str: String) -> crate::GenericResult<(String, String)> {
                let mut split = str.split_whitespace();
                let param = split.next().ok_or(Error {})?;
                let value = split.next().ok_or(Error {})?;
                Ok((param.to_string(), value.to_string()))
	    }
	}
    }
}
```
</details>

----

Другое решение – явное преобразование одного типа ошибки в другой при помощи
метода `Result::map_err`.  Этот метод универсален.  Он, в принципе, позволяет
добавить любую информацию в точке преобразования. Главный его недостаток –
быстро нарастающая громоздкость записи, что лишает смысла магию знака
вопроса. Кроме того, преобразование `Option` в `Result` выглядит по-другому –
`Option::ok_or`, что мешает согласованному восприятию. Как гласит одна из
мудростей программирования, "программы всегда пишутся для людей, и лишь иногда
исполняются машиной".

### Амбула

Конечно, для помощи в преодолении всех этих проблем было создано немало крейтов,
например известный [**thiserror**](https://docs.rs/thiserror/latest/thiserror) с
~700M скачиваний на момент написания этого текста. Мы рассмотрим применение
крейта **SNAFU** – одного из самых зрелых и идейных решений (хотя на порядок
менее популярного с ~70M скачиваний на момент написания этого текста). В отличие
от намеренно компактного **thiserror**, который фокусируется на лаконичности,
**SNAFU** предлагает обширный и согласованный инструментарий для сохранения
контекста ошибки, вплоть до детальной трассировки вызовов функций.

**SNAFU** – большой крейт, предоставляющий множество типов, позволяющих
обрабатывать ошибки с нужной степенью "погружения". Например, есть
функциональность, аналогичная предоставляемой **anyhow**. Но главная ценность,
провозглашаемая философией **SNAFU** – контекст.

Здесь, в этом туториале, мы рассмотрим "мейнстрим" – шаблонное применение лучших
практик **SNAFU**, позволяющее разгрузить мозг от низкоуровневых деталей
обработки ошибок, при этом без компромиссов по качеству. В финальном варианте
программы **SCREP** можно найти самые употребительные паттерны создания,
использования и обработки ошибок в стиле **SNAFU**.

<details>
<summary markdown="span">Окончательная программа screp 0.3.0: фильтровать по регулярным выражениям
(как grep), распознавать параметры, значения и комментарии</summary>

```Rust
//! Simple config reader & expression parser. Parse and grep UnixConf files.
//!
//! [dependencies]
//! clap = { version = "4.5", features = ["derive"] }
//! display-error-chain = "0.2"
//! regex = "1.12"
//! snafu = { version = "0.8", features = ["backtrace"] }
//!
//! Examples:
//!     screp /etc/resolv.conf
//!     screp -s lan /etc/resolv.conf
//!     screp -ps namespace /etc/resolv.conf
//!     screp -vs 192 /etc/resolv.conf
//!     screp -cs Generated /etc/resolv.conf
//!     screp -is g /etc/resolv.conf

use clap::Parser;
use std::path::PathBuf;

/// Simple config reader & expression parser. Parse and grep UnixConf files.
#[derive(Debug, Parser)]
struct Options {
    /// Search case insensitive.
    #[clap(short, long)]
    insensitive: bool,

    /// Search in parameters only.
    #[clap(short, long)]
    param: bool,

    /// Search in values only.
    #[clap(short, long)]
    value: bool,

    /// Search in comments only.
    #[clap(short, long)]
    comment: bool,

    /// Regular expression. Dump all lines if not set.
    #[clap(short, long)]
    search: Option<String>,

    /// Name of the input file.
    filename: PathBuf,
}

fn main() {
    use display_error_chain::DisplayErrorChain as report;

    if let Err(err) = rep::process(Options::parse()) {
        eprintln!("{}", report::new(err));
        std::process::exit(1);
    }
}

mod rep {
    use snafu::prelude::*;
    use std::{fs, io, path::PathBuf};

    #[derive(Debug, Snafu)]
    pub enum Error {
        #[snafu(display("Wrong option: {reason}"))]
        Option { reason: &'static str },

        #[snafu(display("Could not open {:?}", filename))]
        Open {
            source: io::Error,
            filename: PathBuf,
        },

        #[snafu(display("Could not interpret file {:?}", filename))]
        Read {
            source: reader::Error,
            filename: PathBuf,
        },
    }

    pub fn process(opts: crate::Options) -> Result<(), Error> {
        check(&opts)?;
        let filename = opts.filename;
        let file = fs::File::open(&filename).context(OpenSnafu {
            filename: filename.clone(),
        })?;
        if let Some(pattern) = opts.search {
            reader::filter(
                opts.insensitive,
                opts.param,
                opts.value,
                opts.comment,
                pattern,
                io::BufReader::new(file),
            )
            .context(ReadSnafu {
                filename: filename.clone(),
            })?;
        } else {
            reader::dump(io::BufReader::new(file)).context(ReadSnafu { filename })?;
        }
        Ok(())
    }

    fn check(opts: &crate::Options) -> Result<(), Error> {
        if opts.search.is_none() {
            ensure!(
                !opts.insensitive,
                OptionSnafu {
                    reason: "-i without -s"
                }
            );
            ensure!(
                !opts.param,
                OptionSnafu {
                    reason: "-p without -s"
                }
            );
            ensure!(
                !opts.value,
                OptionSnafu {
                    reason: "-v without -s"
                }
            );
            ensure!(
                !opts.comment,
                OptionSnafu {
                    reason: "-c without -s"
                }
            );
        }
        Ok(())
    }

    mod reader {
        use regex::RegexBuilder;
        use snafu::prelude::*;
        use std::io;

        #[derive(Debug, Snafu)]
        pub enum Error {
            #[snafu(display("Could not read"))]
            Read { source: io::Error },

            #[snafu(display("Could not parse line {n}"))]
            Parse { source: parser::Error, n: usize },

            #[snafu(display("Invalid regular expression"))]
            Regex { source: regex::Error },
        }

        pub fn dump<R: io::BufRead>(reader: R) -> Result<(), Error> {
            for line in reader.lines() {
                println!("{}", line.context(ReadSnafu)?);
            }
            Ok(())
        }

        pub fn filter<R: io::BufRead>(
            insensitive: bool,
            check_param: bool,
            check_value: bool,
            check_comment: bool,
            pattern: String,
            reader: R,
        ) -> Result<(), Error> {
            let regex = RegexBuilder::new(&pattern)
                .case_insensitive(insensitive)
                .build()
                .context(RegexSnafu)?;
            for (n, line) in reader.lines().enumerate() {
                let n = n + 1; // Let's count lines from 1
                let line = line.context(ReadSnafu)?;
                if is_string_whitespace(&line) {
                    continue;
                }
                let (param, value, comment) = parser::parse(&line).context(ParseSnafu { n })?;
                let mut show = if !check_param && !check_value && !check_comment {
                    regex.is_match(&line)
                } else {
                    false
                };
                if check_param {
                    show = show || regex.is_match(&param);
                }
                if check_value {
                    show = show || regex.is_match(&value);
                }
                if check_comment {
                    show = show || regex.is_match(&comment);
                }
                if show {
                    println!("{line}");
                }
            }
            Ok(())
        }

        fn is_string_whitespace(s: &str) -> bool {
            s.chars().all(|c| c.is_whitespace())
        }

        mod parser {
            use snafu::prelude::*;

            #[derive(Debug, Snafu)]
            pub enum Error {
                #[snafu(display("Unsupported file format"))]
                Syntax,
            }

            /// Return parts of a config line: param, value and comment (if any).
            pub fn parse(line: &str) -> Result<(String, String, String), Error> {
                let mut split = line.split_whitespace();

                let param = split.next().context(SyntaxSnafu)?;
                if param.starts_with('#') {
                    return Ok((String::default(), String::default(), line.to_string()));
                }

                let value = split.next().context(SyntaxSnafu)?;

                let mut comment = String::default();
                if let Some(third) = split.next() {
                    if !third.starts_with('#') {
                        return SyntaxSnafu.fail()?;
                    } else {
                        let mut split = line.split('#');
                        let _ = split.next().context(SyntaxSnafu)?;
                        comment = split.next().context(SyntaxSnafu)?.to_string();
                    }
                }

                Ok((param.to_string(), value.to_string(), format!("#{comment}")))
            }
        }
    }
}
```

<a name="rule1"></a>
### 1. Контекст превыше всего. Не отбрасывайте контекст без нужды

Плохо, когда программа выдаёт короткое малопонятное сообщение об ошибке вроде
"Error: file not found". Практически всегда нужен контекст: последовательность
ошибок, приведших к этой, конкретные имена объектов, стек вызовов функций...

Типичный шаблон определения ошибки с контекстом:

```Rust
use snafu::prelude::*;

// Определение:
#[derive(Debug, Snafu)]
pub enum Error {
#[snafu(display("Could not open {:?}", filename))]
    Open {
        source: io::Error,
        filename: PathBuf,
    },
...
}

// Сигнатура функции:
pub fn process(...) -> Result<(), Error>

// Использование:
let file = fs::File::open(&filename).context(OpenSnafu { filename })?;
```

Видим, как ошибка `Error::Open` ссылается на `io::Error` благодаря существованию
поля `source` (см. третье правило), что обеспечивает вывод полного стека ошибок.

В метод `context` передаётся не сама ошибка, а её селектор контекста
(см. четвёртое правило).

Итоговый вывод при отсутствии файла:
```
Could not open "/tmp/nonexist"
Caused by:
  -> No such file or directory (os error 2)
```

<a name="rule2"></a>
### 2. Описывайте ошибки на уровне модуля

Каждый модуль должен иметь свой набор ошибок, которые используются только в этом
модуле и больше нигде. Делать единственный "модуль ошибок" для использования по
всему проекту – распространённый антипаттерн. Поскольку ошибки очень часто
бывают "наведёнными", то есть имеющими `source`, это поле естественным образом
заполняется ошибкой зависимого модуля. Таким образом, иерархия ошибок повторяет
иерархию модулей, что помогает сохранять важную часть контекста – "путь" в этой
иерархии от конкретной ошибки к изначальной.

Итак, "на автомате" заводим в каждом модуле `enum Error`, инструментированный для
использования **SNAFU**. И возвращать из функций будем `Result<..., Error>` (или можно
определить алиас).

```Rust
#[derive(Debug, Snafu)]
pub enum Error {
    ...
}
```

Иерархия модулей в программе **SCREP**:
```
top
    rep
        reader
            parser
```

Итоговый вывод при попытке распарсить файл не того формата:
```
Could not interpret file "/etc/passwd" -- из модуля rep
Caused by:
  -> Could not parse line 1  -- из модуля reader
  -> Unsupported file format -- из модуля parser
```

<a name="rule3"></a>
### 3. Добавляйте в ошибку поле `source` для сохранения связи с "родительской" ошибкой

Поле `source` используется и обрабатывается особым образом (начиная с версии **0.8**). Оно не должно
присутствовать в `display`, потому что будет выведено автомагически. Его тип
должен соответствовать типу предыдущей ошибки, и тогда `source` инициализируется
также автомагически, сокращая бойлерплейт.  Если предыдущей ошибки нет, т.е. наша
ошибка – первая в цепочке, то поле `source` опускается.

Так ошибки в модуле `reader` могут ссылаться на ошибки используемого
модуля `parser`:

```Rust
#[derive(Debug, Snafu)]
enum Error {
    ...
    #[snafu(display("Could not parse line {n}"))]
    Parse { source: parser::Error, n: usize },
    ...
}
```

Сгенерировать самую первую ошибку без `source` поможет макрос `ensure`,
напоминающий `assert`:

```Rust
#[derive(Debug, Snafu)]
pub enum Error {
    #[snafu(display("Wrong option: {reason}"))]
    Option { reason: &'static str },
    ...
}
```
```Rust
ensure!(!opts.insensitive, OptionSnafu { reason: "-i without -s" });
```

Ошибку без `source` можно также создать, передав её селектор в метод `OptionExt::context`
(см. пример для следующего правила).

<a name="rule4"></a>
### 4. При обработке ошибки используйте селекторы контекста, а не сами типы ошибок

Селектор контекста – вспомогательный тип, помогающий упростить работу с
контекстом. Он генерируется макросом `#[snafu]` в пару каждой ошибке, так что можно
просто запомнить, что в метод `context()` надо передать значение типа
`<имя-ошибки>Snafu`. Суффикс `Snafu` можно перенастроить на другой. Метод `context()`
принадлежит трейтам `ResultExt` и `OptionExt`, так что обработка отсутствия значения
в `Option` выглядит точно так же, как обработка ошибки `Result`.

Пример создания ошибки `Error::Regex`:
```Rust
#[derive(Debug, Snafu)]
pub enum Error {
    ...
    #[snafu(display("Invalid regular expression"))]
    Regex { source: regex::Error },
}
```
```Rust
let regex = RegexBuilder::new(&pattern)
    .case_insensitive(insensitive)
    .build()
    .context(RegexSnafu)?;
```

Пример создания ошибки по результату `Option`:
```Rust
#[derive(Debug, Snafu)]
pub enum Error {
    #[snafu(display("Unsupported file format"))]
    Syntax,
}
```
```Rust
let value = split.next().context(SyntaxSnafu)?;
```

<a name="rule5"></a>
### 5. Не переиспользуйте типы: в разных контекстах должны появляться разные ошибки

Это очень важное правило.  Иногда возникает соблазн сэкономить на описании новой
ошибки, повторно использовав существующую. Но это приводит к смешению контекстов
и уменьшает информативность итогового сообщения. Совершенно нормально заводить
ошибки, как говорится, "на каждый чих".

<a name="rule6"></a>
### 6. Предоставьте выбор формата и объёма сообщения об ошибке самому верхнему уровню

Это правило означает, что обработка ошибок на средних уровнях должна сводиться к
пробросу ошибки (опционально обогащённой контекстом) вверх по стеку вызовов. Не
стоит пытаться выводить в лог промежуточные сообщения. Тем самым код обработки
становится максимально лаконичным.

На итоговое сообщение верхнего уровня возлагается обязанность проследить всю
цепочку ошибок.  Это хотя и несложная, но громоздкая процедура, поэтому
существуют специальные крейты для форматирования сообщений об ошибках. В нашем
примере используется крейт [**display_error_chain**](https://docs.rs/display-error-chain/latest/display_error_chain):

```Rust
fn main() {
    use display_error_chain::DisplayErrorChain as report;

    if let Err(err) = rep::process(Options::parse()) {
        eprintln!("{}", report::new(err));
        std::process::exit(1);
    }
}
```

<a name="rule7"></a>
### 7. Проектируйте сверху вниз: сначала ошибки модуля, потом ошибки зависимых модулей

Это правило вытекает из общего принципа проектирования сверху вниз, оказавшегося
полезным при использовании императивных языков.

<a name="rule8"></a>
### 8. Субъективная "перегрузка" модуля ошибками является сигналом о желательности рефакторинга для разбиения модуля на подмодули

Система ошибок на уровне модулей помогает вовремя установить момент (например,
`enum Error` разросся и его стало трудно поддерживать), когда модуль стал
слишком большим и требует разбиения на подмодули. Кроме того, если ошибки разных
модулей не компонуются естественным образом, это указывает на плохую
согласованность интерфейсов вообще и мотивирует пересмотреть и улучшить их.

### Заключение

До недавних пор было принято считать, что Rust не имеет общепризнанной стратегии
обработки ошибок. Крейт **SNAFU**, достигший высокой степени зрелости в своей версии
**0.8**, является кандидатом на звание стандарта де-факто в этой области.
