# SNAFU на практике

КДПВ

"Errors are values" -- Rob Pike

## TLDR; Правила SNAFU

- Контекст превыше всего. Не отбрасывайте контекст без нужды

- Описывайте ошибки на уровне модуля, а не крейта. Каждый нетривиальный модуль
  будет иметь свой набор ошибок. Иерархия ошибок будет воспроизводить иерархию
  модулей

- Добавляйте в ошибку поле source (см. ниже) для сохранения связи с предыдущей

- При выдаче ошибки используйте селекторы контекста (см. ниже), а не сами типы
  ошибок

- Не переиспользуйте типы: в разных контекстах должны появляться разные ошибки

- Предоставьте выбор формата и объёма сообщения об ошибке самому верхнему уровню

- Проектируйте сверху вниз: сначала ошибки модуля, потом ошибки зависимых модулей

- Субъективная "перегрузка" модуля ошибками является сигналом о желательности
  рефакторинга для разбиения модуля на подмодули

## Преамбула

Обработка ошибок -- часто болезненная тема программирования. Это необходимая,
но, скажем прямо, обычно скучноватая часть работы, отвлекающая от создания и
реализации увлекательных алгоритмов. Как бы она ни реализовывалась -- через
числовые коды возврата, исключения или монады, -- обработка ошибок порождает
избыточные программные строки (бойлерплейт), что увеличивает когнитивную
нагрузку на разработчика.

Проектировщики языка Rust сделали попытку выбрать лучшие идеи по обработке
ошибок для реализации в этом популярном языке программирования. Rust не
отказывается от исключений (panic), но в качестве основной технологии предлагает
монаду Result (тип, инкапсулирующий значение, которое может быть
ошибочным). Result применяется для обработки "обычных" ошибок, panic для ошибок,
"которые не должны возникать". Эта заметка посвящена философии и практике крейта
SNAFU, предназначенного для удобного генерирования Result с контекстом.

## Амбула

По ходу обсуждения будем иллюстрировать идеи на примере реализации разных
вариантов бесполезной утилиты командной строки под названием SCREP -- Simple
Config Reader & Expression Parser. Она предназначена для поиска по содержанию
файлов в текстовом формате Unix Conf, содержащем параметры и их значения через
пробел и позволяющем вставлять комментарии. Типичный файл в таком формате --
известный каждому пользователю Linux файл resolv.conf, содержание которого может
выглядеть так:

```
# Generated by resolvconf

search lan
nameserver 192.168.1.1 # мой роутер
nameserver fd84:561e:cc37::1
```

Для краткости весь программный код, хотя и разбитый на модули (что важно для
иллюстрации обработки ошибок), будем размещать в единственном файле main.rs.

## Белая магия знака вопроса

Rust предоставляет краткий "магический" способ записи обработки
ошибок. Например, в функции построчного чтения и вывода файла reader::read() мы
можем обработать (в данном случае пробросить "наверх" в вызывающую функцию)
ошибки ввода-вывода таким образом:

<details>
<summary markdown="span">screp 0.1.0: читать строки из stdin и выводить их в stdout</summary>


```Rust
fn main() {
    if let Err(err) = rep::process() {
        eprintln!("{err}");
        std::process::exit(1)
    }
}

mod rep {
    use std::io;

    pub fn process() -> io::Result<()> {
        reader::read(io::stdin().lock())
    }

    mod reader {
        use std::io;

        pub fn read<R: io::BufRead>(reader: R) -> io::Result<()> {
            for line in reader.lines() {
                println!("{}", line?);
            }
            Ok(())
        }
    }
}
```
</details>

Программный код выглядит "чистым" благодаря тому, что знак вопроса в контексте
Result (знак вопроса допускается также в контексте Option) раскрывается
компилятором в примерно такие строки:

```rust
match line_result {
    Ok(line) => line,
    Err(err) => return Err(err)
}
```

Таким образом, как будто удалось взять лучшее из двух миров -- возможность
писать код, почти свободный от громоздкой явной обработки ошибок (преимущество
при использовании исключений), при этом сохраняющий обязательность обработки,
простоту и локальность технологии возврата ошибки.

## Чёрная магия Box<dyn Error>

Нет, не так всё просто.

Могут возникнуть несовместимости типов, связанные с устройством генерика
Result<T,E>, потому что функция возвращает только один конкретный Result для
конкретного E. Например, при наивной попытке совместить обработку ошибок
ввода-вывода и парсинга получаем некомпилируемую программу:

-----------------------------------------------------------
pub fn read<R: io::BufRead>(reader: R) -> io::Result<()> {
    for line in reader.lines() {
        let (param, value) = parser::parse(line?)?;
        println!("{param} = {value}");
    }
    Ok(())
}
-----------------------------------------------------------
error[E0277]: `?` couldn't convert the error to `std::io::Error`
pub fn read<R: io::BufRead>(reader: R) -> io::Result<()> {
                                          -------------- expected `std::io::Error`
-----------------------------------------------------------

Одно из решений этой проблемы -- реализованное в стандартной библиотеке
соглашение, что все типы ошибок неявно конвертируются в тип Box<dyn
std::error::Error + Send + Sync + 'static>, который и должны возвращать
функции. Громоздкость конструкций преодолевается применением крейтов вроде
anyhow. Но такое решение во многих случаях неудовлетворительно, так как
"стирает" информацию о типах, обедняя тем самым контекст ошибки.

screp 0.2.0: читать строки из файла, токенизировать их и выводить токены
--------------------------------------------------------------------
pub type GenericError = Box<dyn std::error::Error + Send + Sync + 'static>;
pub type GenericResult<T> = Result<T, GenericError>;

fn main() {
    let mut args = std::env::args();
    let _ = args.next().expect("Отсутствует имя файла программы");
    let file = args.next().expect("Не задано имя входного файла");
    if let Err(err) = rep::process(file) {
        eprintln!("{err}");
        std::process::exit(1)
    }
}

mod rep {
    use std::{fs, io};

    pub fn process(file: String) -> crate::GenericResult<()> {
        let file = fs::File::open(file)?;
        reader::read(io::BufReader::new(file))
    }

    mod reader {
        use std::io;

        pub fn read<R: io::BufRead>(reader: R) -> crate::GenericResult<()> {
            for line in reader.lines() {
                let (param, value) = parser::parse(line?)?;
                println!("{param} = {value}");
            }
            Ok(())
        }

        mod parser {
            #[derive(Debug)]
            struct Error {}
            impl std::fmt::Display for Error {
                fn fmt(&self, f: &mut std::fmt::Formatter) -> std::fmt::Result {
                    write!(f, "Parser Error")
                }
            }
            impl std::error::Error for Error {}

            pub fn parse(str: String) -> crate::GenericResult<(String, String)> {
                let mut split = str.split_whitespace();
                let param = split.next().ok_or(Error {})?;
                let value = split.next().ok_or(Error {})?;
                Ok((param.to_string(), value.to_string()))
            }
        }
    }
}
--------------------------------------------------------------------

Другое решение -- явное преобразование одного типа ошибки в другой при помощи
метода Result::map_err.  Этот метод универсален. Он, в принципе, позволяет
добавить любую информацию в точке преобразования. Главный его недостаток --
быстро нарастающая громоздкость записи, что лишает смысла магию знака
вопроса. Кроме того, преобразование Option в Result выглядит по-другому --
Option::ok_or, что мешает согласованному восприятию. Как гласит одна из
мудростей программирования, "программы всегда пишутся для людей, и лишь иногда
исполняются машиной".

Конечно, для помощи в преодолении всех этих проблем было создано немало крейтов;
самый известный -- thiserror с 682M скачиваний на момент написания этого
текста. Мы рассмотрим применение крейта SNAFU -- одного из самых зрелых и
идейных решений (хотя на порядок менее популярный с 69M скачиваний на момент
написания этого текста). В отличие от намеренно компактного thiserror, который
фокусируется на лаконичности, SNAFU предлагает обширный и согласованный
инструментарий для сохранения контекста ошибки, вплоть до детальной трассировки
вызовов функций.

## Контекст превыше всего. Не отбрасывайте контекст без нужды

Плохо, когда программа выдаёт короткое малопонятное сообщение об ошибке вроде
"Error: file not found". Практически всегда нужен контекст: последовательность
ошибок, приведших к этой, конкретные имена объектов, стек вызовов функций.

SNAFU -- большой крейт, предоставляющий множество типов, позволяющих
обрабатывать ошибки с нужной степенью "погружения". Например, есть
функциональность, аналогичная предоставляемой anyhow. Но главная ценность,
провозглашаемая философией SNAFU -- контекст.

Здесь, в этом туториале, мы рассмотрим "мейнстрим" -- шаблонное применение
лучших практик SNAFU, позволяющее разгрузить мозг от низкоуровневых деталей обработки
ошибок, при этом без компромиссов по качеству.

Окончательный вариант screp 0.3.0: фильтровать по регулярным выражениям (как
grep), распознавать параметры, значения и комментарии.

Типичный пример определения ошибки с контекстом.
--------------------------------------------------------------------
use snafu::prelude::*;

Определение:
    #[derive(Debug, Snafu)]
    pub enum Error {
        #[snafu(display("Could not open {:?}", filename))]
        Open {
            source: io::Error,
            filename: PathBuf,
        },
        ...
    }

Сигнатура функции:
    pub fn process(...) -> Result<(), Error>

Использование:
    let file = fs::File::open(&filename).context(OpenSnafu { filename })?;

Итоговый вывод:
    Could not open "/tmp/nonexist"
    Caused by:
      -> No such file or directory (os error 2)
--------------------------------------------------------------------

Обратите внимание, как ошибка Error::Open ссылается на io::Error благодаря
существованию поля source.

## Описывайте ошибки на уровне модуля

Каждый модуль должен иметь свой набор ошибок, которые используются только в этом
модуле и больше нигде. Делать единственный "модуль ошибок" для использования по
всему проекту -- плохая идея. Поскольку ошибки очень часто бывают "наведёнными",
то есть имеющими source, это поле естественным образом заполняется ошибкой
зависимого модуля. Таким образом, иерархия ошибок повторяет иерархию модулей,
что помогает сохранять важную часть контекста -- "путь" в этой иерархии от
конкретной ошибки к изначальной.

Итак, "на автомате" заводим в каждом модуле enum Error, инструментированный для
использования SNAFU. И возвращать из функций будем Result<..., Error> (или можно
определить алиас).

--------------------------------------------------------------------
    #[derive(Debug, Snafu)]
    pub enum Error {
        ...
    }
--------------------------------------------------------------------

Иерархия модулей в программе SCREP
-----------------------------------
└── rep
    ├── reader
        ├── parser
-----------------------------------

## Добавляйте в ошибку поле source для сохранения связи с предыдущей

Поле source используется и обрабатывается особым образом. Оно не должно
присутствовать в display, потому что будет выведено автомагически. Его тип
должен соответствовать типу предыдущей ошибки, и source тоже инициализируется
автомагически, сокращая бойлерплейт.  Если предыдущей ошибки нет, т.е. наша
ошибка -- первая в цепочке, то поле source опускается.

Обратите внимание, как ошибки в модуле reader могут ссылаться на ошибки
используемого модуля parser:
--------------------------------------------------------------------
    #[snafu(display("Could not parse line {n}"))]
    Parse { source: parser::Error, n: usize },
--------------------------------------------------------------------

## При выдаче ошибки используйте селекторы контекста, а не сами типы ошибок

Селектор контекста -- вспомогательный тип, помогающий упростить работу с
контекстом. Он генерируется макросом #snafu в пару каждой ошибке, так что можно
просто запомнить, что в метод context() надо передать значение типа
<имя-ошибки>Snafu. Суффикс Snafu можно перенастроить на другой. Метод context()
принадлежит трейтам ResultExt и OptionExt, так что обработка отсутствия значения
в Option выглядит точно так же, как обработка ошибки Result.

Пример создания ошибки Error::Regex
-----------------------------------------------
let regex = RegexBuilder::new(&pattern)
    .case_insensitive(insensitive)
    .build()
    .context(RegexSnafu)?;
-----------------------------------------------

Пример создания ошибки по результату Option
-----------------------------------------------
let value = split.next().context(SyntaxSnafu)?;
-----------------------------------------------

## Не переиспользуйте типы: в разных контекстах должны появляться разные ошибки

Это очень важное правило.  Иногда возникает соблазн сэкономить на описании новой
ошибки, повторно использовав существующую. Но это приводит к смешению контекстов
и уменьшает информативность итогового сообщения. Совершенно нормально заводить
ошибки "на каждый чих".

## Предоставьте выбор формата и объёма сообщения об ошибке самому верхнему
   уровню

Это правило означает, что обработка ошибок на средних уровнях должна сводиться к
пробросу ошибки (опционально обогащённой контекстом) вверх по стеку вызовов. Не
стоит пытаться выводить в лог промежуточные сообщения. Тем самым обработка
становится максимально лаконичной.

На итоговое сообщение верхнего уровня возлагается обязанность проследить всю
цепочку ошибок.  Это, хотя и несложная, но громоздкая процедура, поэтому
существуют специальные крейты для форматирования сообщений об ошибках. В нашем
примере используется крейт display_error_chain.

## Проектируйте сверху вниз: сначала ошибки модуля, потом ошибки зависимых
   модулей

Это правило вытекает из общего принципа проектирования сверху вниз, оказавшегося
полезным при использовании императивных языков.

## Субъективная "перегрузка" модуля ошибками является сигналом о желательности
  рефакторинга для разбиения модуля на подмодули

Система ошибок на уровне модулей помогает вовремя установить момент (enum Error
стало трудно поддерживать), когда модуль стал слишком большим и требует
разбиения на подмодули. Кроме того, если ошибки разных модулей не компонуются
естественным образом, это указывает на плохую согласованность интерфейсов вообще
и мотивирует пересмотреть и улучшить их.

## Заключение

До недавних пор было принято считать, что Rust не имеет общепризнанной стратегии
обработки ошибок. Крейт SNAFU, достигший высокой степени зрелости в своей версии
0.8, является кандидатом на звание стандарта де-факто в этой области.
